# 第 1 章：定义目标与边界

## 本章目标
这一章只做一件事：把“我们到底要做什么”说清楚。

做 JsBridge 最怕的不是技术难，而是目标漂移。今天想做通信，明天想做权限平台，后天又想做插件市场，最后任何一块都做不扎实。

## 先用一句话定义 JsBridge
JsBridge 是 JS 与 Native 之间的“协议化通信层”，它负责把调用、响应、错误用统一格式传递，不负责业务本身。

## 最小可行目标（MVP）
第一版只要达成 3 个结果：
1. JS 可以调用 Native。
2. Native 可以把结果回给 JS。
3. 双方能区分成功与失败。

## 非目标（刻意不做）
为了让第一版能闭环，以下能力先不做：
1. 复杂权限系统（如按用户角色做细粒度策略）。
2. 完整插件生态（安装、卸载、版本治理）。
3. 跨端共享同一套运行时代码。

## 为什么先做“边界”
- 有边界，开发顺序才清晰。
- 有边界，测试标准才能落地。
- 有边界，后续重构不会失控。

## 本章产出物
1. 一页需求文档：MVP 目标 + 非目标。
2. 一个最小演示场景：例如 `ping -> pong`（本仓库示例工程的对应场景是 `getUser` 请求-响应与 `timerLog` 流式回调）。
3. 一份验收标准：调用成功、失败、超时如何判定。

> 与本仓库的关系：这份“MVP + 非目标”最终演化为 `docs/01-protocol.md`（协议边界）与 `AGENTS.md` 中的两条核心原则——Protocol consistency（四端协议一致，运行时各自实现）与 Progressive enhancement（除核心协议外一切可插拔）。教程走完后，参考实现在 `js_bridge_android/js-bridge-core`，iOS/Flutter/HarmonyOS 严格对齐同一协议。

## 验收清单
- 团队成员能用同一句话描述项目目标。
- 每个需求都能映射到 3 个 MVP 目标之一。
- 任何“额外想法”都能明确归类为“后续章节”。

## 常见坑
1. 还没打通链路就先做“完美架构”。
2. 把业务逻辑写进桥接层，导致边界模糊。
3. 不写非目标，导致需求无限膨胀。

## 小结
先把目标缩小，才能把系统做稳。第 2 章开始我们直接用系统能力打通第一条 JS-Native 链路。
